# Business route panel: attached brief applied to existing environment data

The global page will show a layered route map, five data-derived measures, a plain-language connection inspector, a text alternative and a local fix preview. Keep the installed React 19/Next.js application and existing CSS theme tokens; add React Flow and dagre within that application rather than creating a separate Vite app or replacing the brand.

Actual data uses the existing authorized multi-engagement snapshot API. Extend its repeatable-read capture with bounded asset criticality, scoped finding remediation/resolution metadata and **already stored** legacy path edges. Seal this projection with the manifest hash and an explicit route-map version. Only customer/operator-marked critical assets become critical nodes. Each connection requires two scoped endpoints and a finding attached to its destination; unresolved, mismatched and foreign references become reported gaps. Deduplicate repeated stored hops. Preserve engagement-qualified identities and never add cross-engagement edges.

Every legacy connection is theoretical, regardless of CVSS, `exploited`, passive finding verdict, subnet basis or stale metadata. Entry annotations come from the stored model's starting asset and are labelled as modelled locations; no Internet→asset hop is invented. Normalized connection-proof collectors remain a separate activation gate. Grades absent from the API stay unavailable. No connection or missing route establishes that the environment is safe.

Actual remediation is credited only for a coverage-gated automatic resolution with a recorded detection-run reference. Manual closure is reported separately as awaiting scan confirmation. Fix-preview switches exist only in component memory and are labelled as simulation; they never change a finding, queue a scan, persist credentials or claim remediation. Link to the existing finding workflow to record work. Compare only captured views with the same selection and route-map version; a missing finding is not counted as fixed. The two most recent completed captures support before/after comparison; these are assessment captures, not falsely renamed scan executions.

The standalone example uses a clearly labelled JSON fixture with 12 systems, 15 connections and two made-up scans. Its expected baseline is eight simple routes, three reachable critical systems and one all-confirmed route; after the two example fixes and one new connection it is six routes, two reachable critical systems and zero all-confirmed routes. It never replaces actual environment data.

Bounded DFS tracks the visited nodes of each simple path, deduplicates connections, enforces work/path budgets, and reports incomplete counts. Reachable critical systems use a separate bounded graph traversal, so enumerating too many routes cannot incorrectly hide a reachable system. Display at most 20 paths; the list never grows large enough to require virtualization. Layout is memoized only from node/edge topology and does not jump when a fix is previewed. Target 300 systems and 600 connections with visible-element rendering.

Checkpoints: (1) sealed actual-data projection and scope tests; (2) pure analyse/preview/compare and fixture cases; (3) layered graph, inspector, filters, captured-history comparison and accessible list; (4) real build, keyboard/mobile checks and measured performance/accessibility results; (5) update the existing PR and leave the local dashboard open. Lighthouse ≥95 is a target to measure, not a promised result before running it. Required real customer/engagement selection is pending user identification because the running preview has only synthetic data.
# Verification results

All implementation checkpoints above are complete for the local engineering slice. 739 frontend tests and 3,468 collectable backend tests pass, with nine backend skips. The backend count explicitly excludes the two unchanged main-branch collection failures in `test_capability_map.py` and `test_crown_jewels.py`. The 23 affected backend cases cover the strict engine, projection, scoped API, sealed remediation text, two-capture history and a mismatched worker assembly that cannot publish. Production build, full type checking and changed-module lint pass. The final capture-lane copy was followed by nine affected frontend tests and another production build.

Lighthouse accessibility measured **100/100** for `/attack-paths` and `/attack-paths/demo` on the final local build. The first inspection found 4.37:1 contrast on amber reachable-node labels; the grouped correction uses the existing primary-text token. The automated score complements, rather than replaces, the keyboard and 360px light/dark inspection. Natural Tab/Enter selection opens an SVG connection; keyboard fix preview lowers the confirmed route count from one to zero, keeps undo available and restores the route on undo. The route list exposes the same three enabling findings in the confirmed-only case. No horizontal overflow was found at 360px, and the temporary viewport and theme changes were restored.

A 300-system/600-connection dagre layout measured **273ms** in the final isolated affected-test run; concurrent suite runs were slower. Computation is bounded and map rendering uses visible elements. This does not establish a production frame-rate or organization-scale discovery benchmark.

Browser→BFF→API→assessment-only worker→PostgreSQL capture on the local preview produces two source-qualified inventory nodes and zero stored connections/marked critical systems, exactly matching its synthetic source records. It does not substitute the example graph. Earlier task-owned stale workers were found publishing a result without the new map; they were stopped after ownership checks. The engine contract is now v2, the assembler source digest is sealed and checked, and a completed result missing its route map requests reassessment. No unrelated service, scan or notification worker was stopped or run.

The dependency audit reports seven high advisories in the existing Next/ESLint-related stack; no React Flow or dagre advisory was reported. A framework-wide dependency upgrade is outside this feature. Raw Lighthouse reports contain private synthetic audit headers and are deliberately excluded from the repository; only these sanitized measurements are recorded.

Remaining external gates: the user must identify/connect the intended real customer/engagement; authoritative cross-engagement environment identity and reviewed normalized connection observations are still unavailable. The panel now consumes stored environment models as theoretical connections, not confirmed organizational attack proofs. The separate example remains made-up. Actual scan execution and lifecycle mutation remain outside the panel.
