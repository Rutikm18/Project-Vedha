# Multi-engagement finding-driven attack graphs: primary-source implementation research

Research date: 13 October 2026. Scope: a defensive organization workspace that selects one or several authorized engagements, explains findings on different systems, and displays only connections warranted by evidence. This note proposes design and engineering rules; it does not certify a real environment or activate new exploit rules.

## Decision

Build a bounded evidence graph before a general attack-path generator. Selecting engagements determines the inventory under review. It does not establish that their machines share an environment, that two matching IPs are one machine, or that one finding enables the next. Keep inventory associations, candidate transitions, supported transitions, and observed execution separate in both the data and the visual language.

The implementable sequence is: authorized selected engagements → scoped asset/finding records → individually explainable local transitions → explicit identity/context/reachability bridges → bounded chains. A missing bridge should remain visible as a specific evidence gap. A combined finding map is useful even when supported cross-system chains equal zero.

## What the references justify

**State-changing transitions, not severity-linked findings.** MulVAL's source joins several prerequisites to an effect. A CVE identifier, CVSS score, critical asset tag or finding title is insufficient to derive execution. BloodHound's access direction likewise explains why edge semantics matter. Use vulnerabilities as supporting records on transitions; retain assets and access states as the connected entities. [MulVAL rules](https://github.com/risksense/mulval/blob/master/kb/interaction_rules.P), [OpenGraph theory](https://bloodhound.specterops.io/opengraph/developer/graph-theory).

**All required conditions must hold together.** An enabling finding, the exact affected service/configuration, directed reachability, actor permissions and a validated consequence form a conjunction. Alternative rules or supporting evidence form alternatives. A UI that draws independent straight arrows for each prerequisite can conceal this AND requirement. This is an implementation inference from MulVAL's rule bodies and BloodHound's traversability contract. [MulVAL rules](https://github.com/risksense/mulval/blob/master/kb/interaction_rules.P), [definition schema](https://bloodhound.specterops.io/opengraph/developer/graph-definition).

**Temporal sequences require retained context.** SAGE preserves actor-victim groupings and timestamps rather than treating every alert as exchangeable. CALDERA separates operation metadata and fact origin. Use those ideas for evidence provenance while keeping modeled possible chains separate from recorded execution. [SAGE episode source](https://github.com/tudelft-cda-lab/SAGE/blob/main/episode_sequence_generation.py), [SAGE graph source](https://github.com/tudelft-cda-lab/SAGE/blob/main/ag_generation.py), [CALDERA reports](https://caldera.readthedocs.io/en/stable/Operation-Results.html).

## Required records and conservative composition predicates

The following is a proposed product contract, not a format accepted automatically from arbitrary finding JSON.

| Record | Required meaning | Conservative predicate |
|---|---|---|
| Selection | Tenant, authorized engagement IDs, sealed evaluation cut and input revisions | Every source belongs to the requesting tenant and explicitly selected authorized engagements. Fail a forbidden selection as a whole; never silently expose partial unauthorized metadata. |
| Environment | Stable organization/environment/site or security-boundary identity with authoritative source | Equal tenant alone does not imply shared network. Environment display names and CIDR overlap are insufficient. Cross-environment access requires an explicit observed trust/reachability bridge. |
| Entity identity | Namespaced stable source ID plus scoped asset references and provenance of equivalence | Cross-engagement merge requires trusted equivalence evidence valid at the evaluation cut. IP/hostname/fqdn/CVE matches can suggest a review candidate but must not merge entities. |
| Service | Asset identity, service instance, transport, port, configuration/version and observation validity | Bind the finding to the exact service used in the transition. TCP/6379 on one assessment cannot silently stand in for a different instance, port, transport or later rebuilt host. |
| Entry state | Actor/scenario, originating system/zone, authentication and permissions | Every chain begins in a declared actor state. A finding scanner's access does not automatically transfer to an external attacker. |
| Reachability | Directed source context → target listener; source/target IDs, protocol/port, permitted action and current evidence | Same subnet, scope CIDR, shared agent or topology proximity does not prove target access. ACL configuration and successful observed access are distinct evidence classes. |
| Finding applicability | Active lifecycle, affected resource and service, rule ID/version and supported consequence | No generic CVE → RCE conversion. Map only an approved rule whose specific prerequisites and output meaning have been validated. Unmapped findings stay visible. |
| Transition | Exact pre-state, output-state, required facts, all source finding IDs and evidence references | Output state must satisfy the next step's exact precondition. Data-read capability cannot be promoted to command execution, arbitrary credential use or administrator rights. |
| Evidence | Immutable source record/revision/hash, collector version, observed time, accepted validity interval, ingested time and withdrawal/supersession | Same actor/scenario/context and compatible validity are required. Unknown time or identity makes cross-assessment composition indeterminate. Observation time is not ingestion time. |
| Chain result | Ordered transition IDs, origin/goal, provenance, state, coverage, limits and model artifact hash | Every displayed connection is explainable. A chain is only as supported as its weakest prerequisite. A supported modeled chain does not claim the complete sequence was observed. |

For evaluation time `t`, a positive modeled conjunction must have each prerequisite supported and usable at `t`; a validity interval must be deliberately assigned from evidence policy. A STIX first/last-observed interval alone does not prove continuous truth between observations. For observed executions, additionally require linked operation/actor context and actual causal/temporal evidence. These are conservative design inferences, not a guarantee supplied by either standard. [STIX observations](https://docs.oasis-open.org/cti/stix/v2.1/os/stix-v2.1-os.html), [PROV invalidation](https://www.w3.org/TR/prov-dm/#term-Invalidation).

## Repository fit and failure areas

Inspected local `manager/backend/app/models/engagement.py`, `asset.py`, `probe_site.py` and `services/asset_resolution.py`.

- Engagements are tenant-scoped; assets have engagement IDs and optional site IDs. Probe sites are tenant-scoped. The global view can safely aggregate authorized selected engagements while retaining these original IDs.
- Existing asset resolution chooses rows by engagement/IP/site and may adopt a legacy null-site row. Its context lookup falls back to global identity on errors. That ingest policy is not cross-engagement equivalence evidence.
- `Asset.environment`, hostname/fqdn, tags and last-seen are present but do not establish stable canonical identity or observation validity. Tags cannot become trusted attack predicates merely because their JSON contains an attractive field name.
- Prior local readiness work has not activated a positive application-data-read adapter. Preserve this gate. The new workspace can provide a truthful combined inventory and explainable evidence gaps immediately; it must not manufacture positive proofs to produce a visually connected chart.

High-priority failure cases to test: repeated private IP on different sites; same hostname after rebuild; two different ports; one-way reachability mistaken for reverse access; observation from a different actor; January vulnerable service combined with October reachability; a withdrawn fact reused from a cached path; accepted-risk mistaken for remediated; read capability escalated to execution; metadata response mistaken for application data; missing bridge treated as false/secure; unselected engagement evidence leaked into a chain; display limits mistaken for complete computation.

## Bounded implementation and presentation

These are proposed defaults to tune through measurement, not research performance claims: at most 20 selected engagements, explicit caps on total fetched findings/assets/evidence and response bytes, at most 100 displayed candidate chains, at most 8 transitions in a chain, a deterministic evaluation/application budget, and a separately reported compute-truncation flag. Bound inputs before constructing graphs; never enumerate all simple paths in an unbounded environment.

Use deterministic ordering and memoized state/rule applications. Preserve all prerequisite references in proof records. When one evidence revision expires or is withdrawn, invalidate dependent derived proofs; historical sealed snapshots remain historical and show their evaluation time and model version. PROV provides the underlying revision/invalidation vocabulary; the reverse-dependency index and limits are our implementation proposal. [PROV-DM](https://www.w3.org/TR/prov-dm/), [MulVAL project scalability work](https://people.cs.ksu.edu/~xou/mulval/).

The global page should show an engagement picker, selected scope and assessment age, simple chain cards and an optional system map. Use plain labels such as “Found on this system”, “Connection observed”, “Access enabled”, and “Evidence needed”. Inventory edges should say “Finding on system” and have no attack-direction arrow. Candidate attack connections should be interrupted/dashed and name the missing prerequisite. Supported transitions can use directed arrows. Provide an accessible ordered textual chain and inspector with source engagement, rule, condition, validity and verification action.

Recommendation for current delivery: aggregate real scoped findings and local readiness first; expose multi-system and cross-engagement composition only through the conservative contract above. A synthetic demonstration can exercise supported bridges for UI testing only when prominently labeled synthetic and isolated from real assessments. Showing zero supported cross-system paths with specific evidence requirements is an honest useful result, not a reason to relax identity or reachability rules.
